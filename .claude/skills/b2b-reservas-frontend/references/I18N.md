# I18N.md — Internacionalização

> O app começa **apenas em pt-BR**, mas toda a estrutura está pronta para adicionar idiomas sem refatoração. Tudo que vai pra tela passa por `t("chave")` — nada de string hardcoded.

---

## 1. Stack

- **i18next** — engine de tradução, pluralização, interpolação.
- **react-i18next** — bindings React (`useTranslation`, `<Trans>`).
- **i18next-browser-languagedetector** — detecta idioma (localStorage → navigator → fallback).
- **i18next-http-backend** — carrega JSONs sob demanda (lazy load por idioma).

```bash
pnpm add i18next react-i18next i18next-browser-languagedetector i18next-http-backend
```

Bundle: ~25KB gzipped no total, todos somados.

> O namespace `zod.json` existe e é carregado, mas **`zod-i18n-map` ainda não está instalado/wired** (`initI18n` não chama `z.setErrorMap`). Quando os forms passarem a usar Zod (ver [`FORMS.md`](./FORMS.md)), adicione a lib e ligue o map.

## 2. Configuração

```ts
// src/lib/i18n/index.ts
import i18n from "i18next";
import LanguageDetector from "i18next-browser-languagedetector";
import HttpBackend from "i18next-http-backend";
import { initReactI18next } from "react-i18next";

export const DEFAULT_LANGUAGE = "pt-BR";
export const NAMESPACES = [
  "common",
  "zod",
  "users",
  "rfp",
  "proposal",
  "hotel-proposal",
  "rfp-list",
  "rfp-search",
] as const;

export async function initI18n() {
  if (i18n.isInitialized) return i18n;        // idempotente (StrictMode chama 2x)

  await i18n
    .use(HttpBackend)
    .use(LanguageDetector)
    .use(initReactI18next)
    .init({
      fallbackLng: DEFAULT_LANGUAGE,
      supportedLngs: [DEFAULT_LANGUAGE],       // só pt-BR por enquanto
      ns: NAMESPACES,                          // todos os namespaces carregados no boot
      defaultNS: "common",
      backend: { loadPath: "/locales/{{lng}}/{{ns}}.json" },
      detection: {
        order: ["localStorage", "navigator"],
        caches: ["localStorage"],
      },
      interpolation: { escapeValue: false },   // React já escapa
      returnNull: false,
    });

  return i18n;
}

export { default as i18n } from "i18next";
```

> A config atual **não** usa `load: "currentOnly"`, `react.useSuspense` nem `z.setErrorMap` — todos os namespaces da lista são declarados em `ns`. `i18n` e `initI18n` são os exports; não há `SUPPORTED_LOCALES` exportado (só `DEFAULT_LANGUAGE` + `NAMESPACES`).

## 3. Estrutura de arquivos

```
public/
└── locales/
    └── pt-BR/                   # único idioma hoje
        ├── common.json          # botões, ações comuns, mensagens globais
        ├── zod.json             # mensagens de erro do Zod (namespace carregado; lib ainda não wired)
        ├── users.json
        ├── rfp.json             # maior namespace — labels do form de RFP
        ├── rfp-list.json
        ├── rfp-search.json
        ├── proposal.json
        └── hotel-proposal.json

src/
└── lib/
    └── i18n/
        ├── index.ts             # init (initI18n, NAMESPACES, DEFAULT_LANGUAGE)
        └── types.d.ts           # type augmentation (ver §6)
```

**Decisão arquitetural:**

Os JSONs servidos ficam **diretamente** em `public/locales/pt-BR/` (ponto único de edição). Não há diretório `src/i18n/` de fontes co-localizadas — cada módulo tem seu namespace em `public/locales/pt-BR/<modulo>.json`. A lista de namespaces vive no array `NAMESPACES` em `index.ts`: ao criar um namespace novo, adicione-o lá **e** crie o JSON.

## 4. Bootstrap do app

```tsx
// src/main.tsx (trecho — ver AUTH.md §7 pro bootstrap completo)
import { I18nextProvider } from "react-i18next";
import { i18n, initI18n } from "@/lib/i18n";
import "@/lib/i18n/types";                 // ativa o type augmentation

initI18n().then(() => {
  createRoot(rootElement).render(
    <StrictMode>
      <I18nextProvider i18n={i18n}>
        {/* QueryClientProvider > AuthProvider > RouterProvider */}
      </I18nextProvider>
    </StrictMode>,
  );
});
```

`initI18n()` é idempotente (guard `i18n.isInitialized`). O app monta dentro do `.then()` — sem top-level await.

### 5.2 Múltiplos namespaces

```tsx
const { t } = useTranslation(["users", "common"]);

t("list.title");              // users.list.title (default = primeiro NS)
t("common:actions.cancel");   // common.actions.cancel (prefixo explícito)
```

### 5.3 Interpolação

```json
{ "welcome": "Olá, {{name}}!" }
```

```tsx
t("welcome", { name: user.name });
```

### 5.4 Pluralização (ICU)

```json
{
  "items_one": "{{count}} item",
  "items_other": "{{count}} itens"
}
```

```tsx
t("items", { count: 1 });    // "1 item"
t("items", { count: 5 });    // "5 itens"
```

### 5.5 `<Trans>` para JSX complexo

Quando a tradução tem markup (link, bold, etc):

```tsx
import { Trans } from "react-i18next";

<Trans i18nKey="terms.accept" ns="auth">
  Aceito os <a href="/terms">termos de uso</a> e a <a href="/privacy">política</a>.
</Trans>
```

```json
{
  "terms": {
    "accept": "Aceito os <1>termos de uso</1> e a <3>política</3>."
  }
}
```

Os números `<1>`, `<3>` correspondem à posição do filho no componente.

## 6. Type-safety

i18next suporta typing via module augmentation. Garante que `t("chave")` é validado em compile time.

```ts
// src/lib/i18n/types.d.ts
import "i18next";
import type common from "../../../public/locales/pt-BR/common.json";
import type rfp from "../../../public/locales/pt-BR/rfp.json";
import type zodNs from "../../../public/locales/pt-BR/zod.json";
// ... demais namespaces (proposal, hotel-proposal, rfp-list, rfp-search)

declare module "i18next" {
  interface CustomTypeOptions {
    defaultNS: "common";
    resources: {
      common: typeof common;
      rfp: typeof rfp;
      zod: typeof zodNs;
      users: typeof common;        // placeholder até users.json ganhar schema próprio
      // ... um por namespace de NAMESPACES
    };
  }
}
```

Agora `t("nonexistent.key")` é erro de tipo. Editor autocompleta chaves. O arquivo é `.d.ts` e deve listar **todos** os namespaces de `NAMESPACES`.

## 7. Integração com forms (Zod)

### 7.1 `zod.json` — mensagens padrão

```json
// public/locales/pt-BR/zod.json
{
  "errors": {
    "invalid_type": "Tipo inválido: esperado {{expected}}, recebido {{received}}",
    "invalid_type_received_undefined": "Campo obrigatório",
    "invalid_string": {
      "email": "E-mail inválido",
      "url": "URL inválida",
      "uuid": "UUID inválido"
    },
    "too_small": {
      "string": {
        "inclusive": "Mínimo {{minimum}} caracteres",
        "not_inclusive": "Mais de {{minimum}} caracteres"
      },
      "number": {
        "inclusive": "Mínimo {{minimum}}",
        "not_inclusive": "Maior que {{minimum}}"
      }
    },
    "too_big": {
      "string": {
        "inclusive": "Máximo {{maximum}} caracteres"
      }
    },
    "invalid_enum_value": "Valor inválido"
  }
}
```

Lib `zod-i18n-map` lê isso automaticamente.

### 7.2 Mensagens customizadas no schema

Use chaves i18n nas mensagens:

```ts
// src/schemas/users/create-user.schema.ts
import { z } from "zod";
import i18n from "@/lib/i18n";

export const createUserSchema = z.object({
  name: z.string().min(1, { message: i18n.t("users:form.validation.nameRequired") }),
  email: z.string().email(), // usa zod-i18n-map → "E-mail inválido"
});
```

**Problema:** `i18n.t()` é chamado quando o módulo é importado, antes do i18n estar pronto. Solução: use função (lazy):

```ts
import i18n from "@/lib/i18n";

const t = (key: string) => i18n.t(key);

export const createUserSchema = z.object({
  name: z.string().min(1, { message: () => t("users:form.validation.nameRequired") }),
});
```

Ou prefira **chaves só pro `zod-i18n-map`** (mensagens padrão de min/max/email) e **componente mostra mensagem específica via `t`** quando a chave do erro estiver custom.

## 8. Formatação de datas, números, moeda

**Datas têm doc próprio:** [`DATES.md`](./DATES.md) cobre formatação com timezone, conversão ↔ UTC, input do usuário, e armadilhas. Use sempre `useFormat()` (definido em `src/hooks/common/use-format.ts`) — ele já injeta o timezone do usuário. A implementação real é enxuta (delega a `createFormatters(getUserTimeZone())` de `@/lib/datetime/format`); o exemplo elaborado abaixo é ilustrativo do padrão.

**Números e moeda** usam `Intl` nativo — zero KB, full i18n support.

```ts
// src/lib/format-numbers.ts
export function formatCurrency(value: number, locale = "pt-BR", currency = "BRL"): string {
  return new Intl.NumberFormat(locale, { style: "currency", currency }).format(value);
}

export function formatNumber(value: number, locale = "pt-BR", options?: Intl.NumberFormatOptions): string {
  return new Intl.NumberFormat(locale, options).format(value);
}

export function formatPercent(value: number, locale = "pt-BR"): string {
  return new Intl.NumberFormat(locale, { style: "percent", maximumFractionDigits: 1 }).format(value);
}
```

Hook reativo ao idioma ativo:

```ts
// src/hooks/use-format.ts (extensão do hook de datas — ver DATES.md)
import { useTranslation } from "react-i18next";
import { useTimezone } from "./use-timezone";
import * as dateFmt from "@/lib/datetime/format";
import * as numFmt from "@/lib/format-numbers";

export function useFormat() {
  const { i18n } = useTranslation();
  const tz = useTimezone();
  const locale = i18n.language;

  return {
    // Datas — delegam pra src/lib/datetime/format.ts
    date: (input: string | Date) => dateFmt.formatDate(input, tz),
    dateTime: (input: string | Date) => dateFmt.formatDateTime(input, tz),
    time: (input: string | Date) => dateFmt.formatTime(input, tz),
    smart: (input: string | Date, now?: Date) => dateFmt.formatSmart(input, tz, now),
    relative: (input: string | Date, now?: Date) => dateFmt.formatRelative(input, locale, now),
    range: (start: string | Date, end: string | Date) => dateFmt.formatRange(start, end, tz),

    // Números — Intl nativo
    currency: (value: number, currency?: string) => numFmt.formatCurrency(value, locale, currency),
    number: (value: number, options?: Intl.NumberFormatOptions) => numFmt.formatNumber(value, locale, options),
    percent: (value: number) => numFmt.formatPercent(value, locale),
  };
}
```

## 9. Switch de idioma

```tsx
// src/components/LanguageSwitcher.tsx
import { useTranslation } from "react-i18next";
import { SUPPORTED_LOCALES } from "@/lib/i18n";
import { Select, SelectContent, SelectItem, SelectTrigger, SelectValue } from "@/components/ui/select";

const LABELS: Record<typeof SUPPORTED_LOCALES[number], string> = {
  "pt-BR": "Português (Brasil)",
  // "en": "English",
  // "es": "Español",
};

export function LanguageSwitcher() {
  const { i18n } = useTranslation();
  if (SUPPORTED_LOCALES.length <= 1) return null; // não mostra se só 1 idioma

  return (
    <Select value={i18n.language} onValueChange={(lng) => i18n.changeLanguage(lng)}>
      <SelectTrigger className="w-40">
        <SelectValue />
      </SelectTrigger>
      <SelectContent>
        {SUPPORTED_LOCALES.map((lng) => (
          <SelectItem key={lng} value={lng}>{LABELS[lng]}</SelectItem>
        ))}
      </SelectContent>
    </Select>
  );
}
```

> Hoje o `index.ts` não exporta `SUPPORTED_LOCALES` (só `DEFAULT_LANGUAGE` e `NAMESPACES`, e `supportedLngs: [DEFAULT_LANGUAGE]` inline). Para um switcher de verdade, exporte um array `SUPPORTED_LOCALES` e use-o em `supportedLngs`.

Adicionar idioma novo no futuro:
1. Crie `public/locales/<lng>/*.json`.
2. Adicione o locale a `supportedLngs` (e a um `SUPPORTED_LOCALES` se exportado).
3. Adicione label em `LABELS`.

Pronto. Sem mudar mais nada.

## 10. Plurais de pt-BR vs en — sutilezas

i18next v23+ usa as regras CLDR. pt-BR e en têm regras **diferentes**:

- en: `_one` (1) + `_other` (resto).
- pt-BR: `_one` (0-1) + `_other` (resto). Sim, zero é singular em português ("0 item" parece estranho — mas o padrão CLDR é assim).

Para "0 itens" em português, use chave própria:

```json
{
  "items_zero": "Nenhum item",
  "items_one": "{{count}} item",
  "items_other": "{{count}} itens"
}
```

(i18next reconhece `_zero` mesmo onde CLDR não define, se você fornece.)

## 12. Testes com i18n

> **No repo, `test/setup.ts` inicializa o i18n real** (via `initI18n`), não o mock abaixo — os testes carregam as traduções de verdade. O mock a seguir é uma alternativa quando se quer asserts por chave; ver [`TESTING.md`](./TESTING.md).

Mock simples no setup do Vitest — devolve a chave em vez do texto. Testes ficam previsíveis sem depender do conteúdo das traduções.

```ts
// test/mocks/i18n.ts
import { vi } from "vitest";

vi.mock("react-i18next", () => ({
  useTranslation: () => ({
    t: (key: string) => key,         // retorna a chave
    i18n: { language: "pt-BR", changeLanguage: vi.fn() },
  }),
  Trans: ({ i18nKey }: { i18nKey: string }) => i18nKey,
  initReactI18next: { type: "3rdParty", init: () => {} },
}));
```

Em `test/setup.ts`:

```ts
import "./mocks/i18n";
```

Asserts ficam:

```tsx
expect(screen.getByText("users:list.title")).toBeInTheDocument();
```

Não é o mais "realista", mas é estável e rápido. Para testes onde a tradução **importa** (validação de erro Zod traduzido), inicialize i18n real com fixture mínima.

## 13. CLAUDE Code — regras

- **Nada hardcoded.** Todo texto visível é `t("chave")` ou `<Trans>`.
- **Mensagens de erro de API** vêm do backend e **não passam por i18n no front** — backend já manda em pt-BR (ou no idioma do `Accept-Language` se implementarmos).
- **Logs / erros console** ficam em inglês (são pra dev, não usuário).
- **Comentários no código** em inglês (padrão).
- **Strings dentro de schemas Zod** sempre via chave i18n (ver §7.2).
- **Datas, moedas, números** sempre via `useFormat()`. Datas em particular têm regras complexas de timezone — leia [`DATES.md`](./DATES.md) antes de tocar.
- **Chave de tradução** segue o padrão `<feature>:<contexto>.<sub>`. Ex: `users:form.fields.email`, `common:actions.save`.

## 14. Adicionar inglês depois — checklist

1. Crie `public/locales/en/` espelhando estrutura de pt-BR.
2. Traduza cada JSON.
3. Adicione `"en"` em `SUPPORTED_LOCALES` em `src/lib/i18n/index.ts`.
4. Adicione `"en": "English"` em `LABELS` no `LanguageSwitcher`.
5. Atualize types em `src/lib/i18n/types.ts` (opcional, pt-BR é o "schema canônico").
6. Teste com `?lng=en` ou trocando em `localStorage.setItem("i18nextLng", "en")`.

**Sem mudanças no código de componentes.**
